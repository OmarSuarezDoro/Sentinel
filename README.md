# Sentinel · MSSP Security Manager

Sentinel is an internal security operations platform for managed security service providers. It brings each client's assets, safeguards, findings, risks, providers, and corrective actions into one workspace, with a 3D view of defense in depth and reports delivered exclusively to a configured internal mailbox.

The application interface is in Spanish. This repository's documentation is in English.

**Stack:** Next.js App Router, React, TypeScript, Tailwind CSS, Three.js, Express, Prisma, and PostgreSQL 17. Docker Compose runs the application locally behind Nginx.

## Quick start

Install Docker Engine with Docker Compose v2. For guided configuration, also install Node.js 22 or later, then run these commands from the repository root:

```bash
npm ci
npm run onboarding
npm run onboarding:check
docker compose up -d --build
```

The local assistant prepares `.env`, asks for missing settings, generates a private installation key, and preserves existing database credentials. It never prints secrets. If PostgreSQL data already exists and its password is missing, restore the original credential before continuing.

Open [http://localhost:8080](http://localhost:8080). The first-run screen checks the database and schema, then lets you create the administrator using `ONBOARDING_TOKEN` from your local `.env`. Use a password of at least 12 characters. Once users exist, initial registration closes automatically.

After signing in, open **Onboarding** to review configuration and customize each client/tenant: display name, initials, identification color, and welcome message. The screen also links to client locations, reporting settings, assets, and security checks. See the [onboarding guide](docs/onboarding.md) for details.

For a Docker-only installation, copy `.env.example` to `.env`, configure the PostgreSQL settings, internal report mailbox, and administrator credentials, then run:

```bash
mkdir -p infrastructure/postgres/data infrastructure/storage/attachments infrastructure/backups/postgres
docker compose up -d --build
docker compose run --rm backend npm run db:seed
```

This alternative creates the administrator from `ADMIN_EMAIL` and `ADMIN_PASSWORD`. There is no default password. The seed does not change an existing user's password; editing `.env` alone does not create or reset an account.

To add explicitly fictional demo data:

```bash
docker compose run --rm -e SEED_DEMO=true backend npm run db:seed
```

The API and worker start after the `migrate` service applies versioned migrations. PostgreSQL has no published port; Nginx listens on `127.0.0.1:8080`. Database files live in `infrastructure/postgres/data` and attachments in `infrastructure/storage/attachments`. `docker compose down` preserves these directories.

Application containers run as `node` (UID 1000). The attachment directory must be writable by that UID; adjust ownership or permissions if the host uses a different UID.

### Sign-in troubleshooting

If login fails, check the email and password against the account originally created. For a fresh database, run the seed command above and confirm it completes successfully. You can also open `/setup` to review database/schema status. A password shorter than 12 characters prevents initial administrator creation. If the account already exists, an administrator must reset its password through user management; running the seed again preserves it.

```bash
docker compose ps
docker compose logs --tail 50 backend migrate
```

## Configuration

Use [.env.example](.env.example) as the configuration reference. Keep credentials in the environment and out of frontend code.

| Variable | Purpose |
| --- | --- |
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | PostgreSQL initialization and Compose connection settings |
| `DATABASE_URL` | Prisma connection for backend commands outside Compose; Compose supplies the container connection |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD`, `ADMIN_NAME` | Optional administrator seed configuration; the protected web setup is an alternative |
| `ONBOARDING_TOKEN` | Private key for first-user web setup; generated by the local assistant and ignored once users exist |
| `INTERNAL_REPORT_EMAIL` | Single permitted internal report recipient; delivery is blocked without a valid value |
| `COOKIE_SECURE` | Set to `true` when serving the application over HTTPS |
| `SUMMARY_ADAPTER` | `template` or `local-llm` |
| `MAIL_ADAPTER` | `microsoft-graph` or `disabled` |
| `GRAPH_TENANT_ID`, `GRAPH_CLIENT_ID`, `GRAPH_CLIENT_SECRET`, `GRAPH_SENDER` | Microsoft Graph delivery credentials and sender mailbox |
| `LOCAL_LLM_URL`, `LOCAL_LLM_MODEL` | Optional local summary endpoint and model |
| `API_INTERNAL_URL` | Next.js backend proxy target, set when building; defaults to `http://localhost:4000` for local development |

## Working with Sentinel

### Client posture and inventory

- Create clients, contacts, physical sites, and cloud environments. Assign assets, controls, and responsible providers to locations.
- Use the client dashboard and operational security review to track backup systems, restoration procedures, server hardening, mail filtering, unresolved vulnerabilities, and high availability for critical network equipment. New clients receive verification tasks even before assets are registered.
- Manage servers, networks, services, and aggregate endpoint or identity groups. Groups declare a total population and can contain detailed individual records. Individuals are managed from their group rather than the main inventory.
- Search inventory by name, IP, hostname, email, attributes, accounts, interfaces, or annotations. Asset pages include technical details, authored notes, evidence, relationships, and recorded security signals.
- Import assets through a UTF-8 CSV with preview and row validation: up to 1 MB and 200 assets per batch. The parser accepts English headers such as `name` and `type`, or Spanish `nombre` and `tipo`; networks also require `cidr`. Optional fields include IP, hostname, email, and an existing site. Invalid rows, duplicates, or overlapping networks prevent the entire batch from being saved. Existing assets are not overwritten.

See [asset groups and partial coverage](docs/asset-groups.md) and [control layers](docs/control-layers.md) for inventory rules and effective coverage calculations.

### Defense in depth, providers, and connectivity

The Three.js visualization fills the workspace and represents sites, cloud environments, and providers. Selecting a location reveals seven defense layers and a contextual panel of controls, assets, and findings. Camera controls include rotation, pause, orbit, and zoom; reduced motion and a fallback without WebGL are supported. Layer colors identify categories, while documented controls and verified coverage are shown separately.

Provider pages bring together contacts, services, locations, linked assets, access records, responsibilities, and annotations. External access records document site-to-site, user, and provider VPNs and appear in the visualization. These are documented connections, not live tunnel configuration or monitoring.

### Findings, tasks, risks, and compliance

Vulnerabilities, audits, and tasks retain owners, deadlines, status, evidence, and an operation history. Mitigated findings remain open until effectiveness is validated. Closing a finding requires prior mitigation and validation evidence; blocked tasks require a reason, and changing an existing deadline requires justification.

Tasks appear in a numbered list ordered by criticality, with a doughnut chart showing counts and percentages across the complete filtered result set. Each task opens its details, editing actions, and follow-up notes. Automated security tasks close or reopen from their source checks without duplication.

The shared risk catalog contains 40 base internal scenarios and supports administrator-managed definitions. Analysts select definitions when assessing a client; each assessment preserves the selected version and methodology snapshot. `MSSP-*` codes are internal references, not official MAGERIT identifiers. Risk assessment remains qualitative and manual.

The compliance area adds an internal NIS2 checklist, evidence, linked operational records, requirement follow-up tasks, and a SWOT workspace. It supports assessment rather than automatic certification or a legal determination of applicability. See [NIS2 compliance](docs/compliance-nis2.md).

### Internal reporting

Reports preserve data snapshots and communicated items. They support generation, review, editing, approval, and manual delivery. Editing revokes approval. The worker schedules reports by client, weekday, hour, and time zone; automatic delivery requires an explicit client policy. Weekly reports always include pending automated security tasks.

**Reports are sent only to `INTERNAL_REPORT_EMAIL`.** Client email addresses, contacts, and historical recipient preferences are not delivery targets. The API rejects recipient edits and the Graph adapter enforces the single configured address, without CC or BCC. Missing recipient configuration or Graph credentials blocks delivery.

Critical findings also create internal notifications at `GET /api/v1/clients/:clientId/notifications` and can be used to prepare an extraordinary report before the weekly schedule.

## Access and security

| Role | Access |
| --- | --- |
| `admin` | All clients, client creation, user administration, and configuration |
| `analyst` | Operations and reports for assigned clients |
| `auditor` | Read access to assigned clients; write access to audits, findings, and their evidence/comments; no report approval or delivery |

Backend authorization covers record IDs, relationships, history, and attachment downloads. Cross-client relationships are prevented by tenant-scoped checks and composite foreign keys. Writes use optimistic version checks, soft archiving, and audit records.

Sessions use HttpOnly, SameSite=Strict cookies with an eight-hour lifetime. Opaque session tokens are stored as SHA-256 hashes; passwords use Argon2id. Authenticated writes require CSRF protection, cross-site writes are rejected, and authentication/request rate limits apply. Inventory fields reject stored credentials. Evidence uploads support PNG, JPEG, PDF, and TXT files up to 5 MB.

For public exposure, terminate TLS at the proxy or upstream infrastructure and set `COOKIE_SECURE=true`. The supplied deployment is intended for local access.

## Integrations

### Microsoft 365

Select `MAIL_ADAPTER=microsoft-graph` and configure the `GRAPH_*` variables. The adapter uses client credentials and Graph `sendMail`. Configure the Entra application with the `Mail.Send` application permission, administrator consent, and mailbox access restrictions appropriate to your organization. Keep the client secret on the backend.

Delivery transitions atomically from `approved` to `sending`, then to `sent` on confirmed success. Errors or timeouts produce `delivery_unknown` for review. Delivery is not automatically retried: check the mailbox before allowing another attempt, because `sendMail` does not provide end-to-end idempotency. `MAIL_ADAPTER=disabled` explicitly rejects delivery.

### Optional local summaries

Use `SUMMARY_ADAPTER=template` without a model, or select `local-llm` with an endpoint compatible with Ollama's `/api/generate` contract:

```dotenv
SUMMARY_ADAPTER=local-llm
LOCAL_LLM_URL=http://your-private-server:11434/api/generate
LOCAL_LLM_MODEL=llama3.2
```

Only structured data for the current client is sent, without credentials or attachments. The adapter applies a 15-second timeout, an output limit, and numerical checks against the snapshot. Failures fall back to the deterministic template. Generated narratives are assisted drafts requiring human review; automated checks cannot guarantee semantic accuracy. The model does not modify records or calculate metrics. Use a private endpoint when local-only processing is required.

## Local development

Install Node.js 22 and provide an accessible PostgreSQL database. From the repository root:

```bash
npm ci
npm run db:generate
# Load the backend environment variables into your shell first.
# Set DATABASE_URL to the PostgreSQL instance used for development.
npm run db:deploy -w backend
npm run db:seed -w backend
npm run dev:api
# In another terminal:
npm run dev:web
```

The frontend runs at [localhost:3000](http://localhost:3000) and proxies API requests to [localhost:4000](http://localhost:4000) by default. Backend routes use `/api/v1`; `GET /api/v1/health` checks the actual PostgreSQL connection. The Compose database is not exposed to the host, so provide a separate development database or an explicit local port mapping.

## Verification

```bash
npm run build
npm test
# Use a disposable database whose name includes mssp_test:
DATABASE_URL=postgresql://user:password@localhost:5432/mssp_test npm run db:deploy -w backend
DATABASE_URL=postgresql://user:password@localhost:5432/mssp_test npm run test:integration -w backend
```

Integration tests create and clean up their own users and clients. They cover authorization, tenant isolation, CSRF, versioning, relationships, networking, validated closure, evidence, reporting, and module-specific workflows. They do not send real email. Historical verification results and screenshots are documented in [VERIFICATION.md](docs/VERIFICATION.md) and the feature guides below; recorded counts describe those runs rather than a fresh verification of every checkout.

## Updates, backups, and recovery

Back up the database and preserve attachments before updating. To rebuild, apply migrations, and update the application services:

```bash
./scripts/backup.sh
docker compose build migrate backend worker frontend
docker compose run --rm migrate
docker compose up -d backend worker frontend
```

For recovery:

```bash
# Replaces all data in the configured database and stops writer services:
./scripts/restore.sh --confirm-replace infrastructure/backups/postgres/backup.dump
```

Backups use the custom `pg_dump` format. A bind mount is not a backup, and the database dump contains attachment metadata rather than file contents. Keep a consistent copy of attachments, periodically restore into an isolated database, compare record counts, and run functional checks. Define retention, encryption, off-host storage, RPO, and RTO for production.

## Repository layout

```text
frontend/src/app/           Routes, layout, and shared styles
frontend/src/features/      Workspace, forms, and feature views
frontend/src/lib/           HTTP client and shared frontend utilities
backend/src/modules/       Domain routes, controllers, services, DTOs, and tests
backend/src/middleware/    Authentication, authorization, and request parsing
backend/src/shared/        Domain rules and database access
backend/src/integrations/  Mail and summary adapter families
backend/src/jobs/          Background worker
backend/prisma/            Schema, versioned migrations, seed, and risk catalog
backend/tests/             Architecture, domain, middleware, and HTTP integration tests
docs/                      Architecture and feature guides
artifacts/                 Verification screenshots and review notes
scripts/                   Backup, recovery, and brand asset utilities
```

Inventory modules share a `Record` table for common fields and JSONB for category-specific attributes. Accounts, grants, interfaces, provider access, control deployments, locations, groups, evidence, assessments, reports, deliveries, and audit history use relational entities. Controllers receive validated requests and delegate through an Express-independent operation context; integration adapters are selected at startup.

## Current limitations

Production preparation still includes internal MFA, attachment antivirus scanning, load testing, deployment-specific TLS certificates, and quantitative availability, retention, and recovery policies. Full MAGERIT implementation and a client-facing portal remain later PRD phases. Real Microsoft 365 delivery and local model inference require operator-provided configuration; the historical checks do not establish those integrations as verified in your environment.
